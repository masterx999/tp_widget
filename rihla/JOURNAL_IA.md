| Question posée à l'IA | Réponse utile | Ce que j'ai compris (proposition à personnaliser) |
| --- | --- | --- |
| **Palier 0 —** Quel code renvoie `/destinations/99` ? À quelle famille appartient-il ? | Si aucune destination n'a cet identifiant, json-server renvoie `404 Not Found`. C'est un code HTTP de la famille `4xx`, qui indique une erreur côté requête/ressource demandée. | Je comprends que `404` signifie que le serveur répond, mais ne trouve pas la destination demandée. |
| **Palier 0 —** Qui choisit l'identifiant de la réservation créée : moi ou le serveur ? | Le serveur json-server attribue l'identifiant au POST. Le client envoie les champs de réservation, sans `id`, puis lit l'`id` dans la réponse `201 Created`. | Je laisse le serveur créer l'identifiant et j'utilise celui qu'il renvoie pour confirmer la réservation. |
| **Palier 0 —** Pourquoi le GET n'a-t-il pas de corps contrairement au POST ? | GET demande une représentation d'une ressource; le chemin et les paramètres identifient les données à lire. POST crée une ressource : son corps JSON contient les champs à enregistrer. | GET demande les données; le corps du POST fournit au serveur les champs de la nouvelle réservation. |
| **Palier 2 —** Pourquoi `fromJson` est-il un constructeur `factory` ? | Il convertit une représentation externe (`Map<String, dynamic>`) en objet `Destination` et peut contrôler ou convertir les valeurs avant de renvoyer l'instance. Le code appelant n'a pas à connaître les détails de conversion. | `fromJson` centralise la création d'une destination à partir des clés JSON et convertit notamment les types numériques. |
| **Palier 2 —** Que se passe-t-il si le JSON contient `"prix": "420"` au lieu d'un nombre ? | Le modèle attend une valeur `num` pour `prix`. Une chaîne n'est pas un nombre JSON et le cast échoue : la conversion signale une erreur plutôt que d'inventer une valeur. Il faut corriger les données ou ajouter une conversion explicitement validée. | Le prix doit rester un nombre dans le JSON; une chaîne mal formée doit faire remonter une erreur au lieu de masquer le problème. |
| **Palier 2 —** Pourquoi `getDestinations` renvoie-t-il `Future<List<Destination>>` ? | Une requête réseau prend du temps et se termine plus tard. Le `Future` représente ce résultat futur; lorsqu'il arrive, il contient la liste convertie. Une `List` immédiate ne peut pas représenter l'attente de la réponse HTTP. | Le `Future` représente la liste qui sera disponible après la réponse réseau, pas une liste déjà chargée. |
| **Palier 3 —** Pourquoi déclarer `_futurDestinations` avec `late` ? | La requête est créée une fois dans `initState`, après que l'état existe. `late` permet de déclarer le champ non nullable avant cette initialisation différée; le `Future` est ensuite réutilisé pendant les reconstructions. | La requête est lancée une seule fois dans `initState`; la conserver évite de refaire un GET à chaque `build()`. |
| **Palier 3 —** Que verrait l'utilisateur sans tester `snapshot.hasError` quand le serveur est arrêté ? | Il ne verrait pas un état d'erreur utile. L'interface pourrait rester bloquée, afficher un état incorrect ou tenter d'utiliser des données absentes. Le contrôle permet d'expliquer la panne et de proposer une nouvelle tentative. | Le test d'erreur permet d'afficher l'indisponibilité du serveur et un bouton de nouvelle tentative plutôt qu'un écran cassé. |
| **Palier 3 —** Le changement de catégorie lance-t-il une nouvelle requête ? Pourquoi ? | Non. La liste téléchargée est filtrée localement en mémoire; changer de puce reconstruit l'écran à partir de cette liste et ne rappelle pas l'API. Une nouvelle requête est réservée au rafraîchissement ou à une tentative après erreur. | Les catégories filtrent la liste déjà reçue; seul le geste d'actualisation ou le bouton réessayer redemande les données. |
| **Palier 4 —** Pourquoi envoyer `destinationId` plutôt que toute la destination ? | La réservation référence la destination par son identifiant. Le serveur peut ainsi relier les deux ressources sans recopier tous les détails de destination dans chaque réservation. L'API peut ensuite inclure la destination avec `_embed`. | La réservation garde une référence courte vers la destination; le serveur peut ensuite retrouver et joindre ses détails. |
| **Palier 4 —** Que se passe-t-il si l'en-tête `Content-Type` est oublié ? | Le client n'indique plus que le corps est du JSON. Le serveur ou un autre endpoint peut alors ne pas le décoder comme prévu et la création peut échouer ou produire des données incorrectes. Il faut envoyer `application/json` avec le corps encodé. | L'en-tête `Content-Type: application/json` indique au serveur comment interpréter le corps envoyé. |
| **Palier 4 —** Pourquoi vérifier `mounted` après `await creerReservation` ? | Pendant l'attente réseau, l'écran peut être retiré de l'arbre (navigation retour). Un état retiré ne doit pas afficher de dialogue ou de SnackBar en utilisant son `context`; `mounted` vérifie que l'écran est encore actif. | L'utilisateur peut revenir en arrière pendant la requête; `mounted` empêche alors d'utiliser le contexte d'un écran fermé. |
| **Palier 5 —** Comment retrouver la destination de chaque réservation ? | La requête `/reservations?_embed=destination` demande à json-server d'inclure l'objet destination lié par `destinationId`. `Reservation.fromJson` convertit cet objet imbriqué avec `Destination.fromJson`. | `_embed` ajoute l'objet destination à la réservation; son convertisseur déjà existant évite de dupliquer le décodage. |
| **Palier 5 —** Pourquoi convertir `dateDepart` avec `DateTime.parse` ? | L'API transporte la date sous forme de chaîne ISO 8601. `DateTime.parse` la convertit en date exploitable par Dart, que l'écran peut afficher au format `jj/mm/aaaa`. | L'API utilise un format de date standard; l'application le convertit pour l'afficher dans un format plus lisible. |
| **Palier 5 —** Pourquoi l'onglet Voyages a-t-il les mêmes états de chargement, erreur et données ? | La liste vient elle aussi du réseau : elle peut être en attente, échouer si le serveur est indisponible, être vide ou contenir des réservations. Le même schéma `FutureBuilder` et le même widget d'erreur rendent chaque état visible et réessayable. | L'onglet affiche l'attente, une erreur récupérable, un message si la liste est vide ou les cartes lorsque les réservations existent. |
